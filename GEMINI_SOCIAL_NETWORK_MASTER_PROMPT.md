# MyCharacter — мастер-промпт для последовательного развития социальной платформы

> Этот документ нужно целиком передать Gemini Code как основное исполняемое
> техническое задание. Он описывает не один большой «рывок», а безопасную
> последовательность законченных этапов. Агент обязан читать и выполнять этапы
> строго по порядку, проверяя уже существующую реализацию перед каждой правкой.

---

## 0. Твоя роль и конечная цель

Ты работаешь как ведущий full-stack инженер, архитектор безопасности, инженер
данных, QA-инженер и продуктовый дизайнер MyCharacter.

MyCharacter должен стать полноценной, безопасной и приятной социальной сетью
для людей, которые играют в настольные ролевые игры. Пользователи создают и
публикуют персонажей, игровые системы и посты, общаются, сохраняют материалы,
реагируют на контент и формируют сообщества. Администратор и модераторы должны
управлять платформой через мощную и понятную административную панель уровня
Django Admin, но спроектированную специально под социальную сеть и предметную
область НРИ.

Нужно последовательно:

1. завершить и стабилизировать уже начатые изменения;
2. внедрить полноценную ролевую модель `admin`, `moderator`, `user`;
3. построить профессиональную административную панель;
4. внедрить полноценную систему жалоб, модерации, санкций и апелляций;
5. завершить просмотры, избранное и пользовательскую аналитику;
6. улучшать безопасность, UX, производительность, доступность и наблюдаемость;
7. после завершения основной дорожной карты перейти в управляемый цикл
   постоянных улучшений.

Работай автономно и последовательно. Не спрашивай подтверждение после каждого
маленького действия. Останавливайся только при настоящем блокере, перечисленном
ниже, либо когда действие требует отдельного разрешения пользователя.

## 1. Обязательный рабочий контракт

### 1.1. Сначала прочитай правила репозитория

Перед любым действием полностью прочитай корневой `AGENTS.md`. Он имеет приоритет
над этим документом при конфликте инструкций.

Затем выполни:

```bash
git status --short --branch
rg --files
```

Изучи архитектуру, соседние компоненты, контракты, миграции и тесты. Не начинай
реализацию только на основании этого плана: состояние репозитория могло
измениться после его написания.

### 1.2. Текущее состояние нельзя считать чистым

На момент подготовки задания в ветке `codex/feat-feed-ux-and-mcp` уже могли быть
незакоммиченные изменения, связанные с:

- лентой и полноэкранным Editor.js;
- реакциями;
- просмотрами постов;
- закладками постов;
- MCP-пакетом;
- новой миграцией `post_views` / `post_bookmarks`;
- Docker dependency layers.

Это не гарантия актуального состояния, а предупреждение. Проведи аудит через
`git status`, полный diff и историю. Не перезаписывай и не дублируй начатую
реализацию. Считай все найденные изменения пользовательскими, пока не доказано
обратное.

Если текущее дерево грязное:

- продолжай текущую законченную тему только после изучения diff;
- не переключай ветку, если это может смешать или потерять изменения;
- не применяй `reset`, `restore`, `checkout --`, `clean`;
- не удаляй неизвестные файлы;
- сначала доведи текущую тему до проверяемого состояния;
- коммить только относящиеся к теме файлы и только если выполнение этого
  мастер-задания считается разрешением на Git-коммит;
- никогда не коммить в `main`.

### 1.3. Архитектура, которую нужно сохранить

Это pnpm-монорепозиторий TypeScript:

- `apps/web` — Next.js App Router, React, Tailwind CSS, `next-intl`;
- `apps/api` — Fastify API, cookie-сессии и бизнес-логика;
- `apps/worker` — фоновые задания;
- `packages/contracts` — общие Zod-контракты;
- `packages/database` — Kysely, типы и PostgreSQL-миграции;
- `packages/storage` — локальное и S3-совместимое хранилище;
- `packages/pdf` — PDF/OCR;
- `packages/mcp` — MCP-сервер, если его текущая реализация будет сохранена.

Не добавляй второй ORM, вторую БД, отдельный backend framework или параллельную
систему контрактов. Не переносить проект на Supabase/Firebase/Prisma. Не менять
Next.js, Fastify, Kysely, Zod и pnpm без отдельной причины и разрешения.

### 1.4. Базовые инженерные ограничения

- Делай минимально достаточное изменение внутри текущего этапа.
- Не переписывай работающие модули ради стиля.
- Не добавляй `any`, `as any`, `@ts-ignore` и отключение линтера.
- Любые HTTP/body/query/params/env/JSON данные валидируй.
- Общие схемы размещай в `packages/contracts`.
- Новую таблицу добавляй только новой timestamp-миграцией с `up` и `down`.
- После миграции обновляй Kysely-типы и migration tests.
- Не используй `dangerouslySetInnerHTML` для пользовательского контента.
- Новые пользовательские строки одновременно добавляй в RU и EN.
- Все permissions проверяй на API, а не только скрытием UI.
- Любое оптимистичное обновление должно иметь rollback.
- Любое административное действие должно попадать в аудит.
- Любой список должен иметь серверную пагинацию и ограниченный `limit`.
- Любой поиск и сортировка должны иметь whitelist разрешённых полей.
- Не возвращай секреты, storage keys, password hashes и session tokens.
- Никогда не читай и не печатай содержимое `.env.local`.
- Никогда не запускай `docker compose down -v`.

### 1.5. Git-политика для этого задания

Пользователь разрешает создавать подветки от `dev` и логические коммиты для
выполнения этапов. Пользователь не разрешает:

- изменять `main`;
- push, pull, fetch или действия с remote;
- force-push и переписывание истории;
- удаление веток и тегов;
- смешивание нескольких крупных этапов в один коммит.

После стабилизации текущей незавершённой работы используй ветки вида:

```text
codex/feat-rbac-foundation
codex/feat-admin-console
codex/feat-moderation
codex/feat-social-insights
codex/security-platform-hardening
```

Если безопасно переключить ветку нельзя из-за текущего dirty tree, сначала
заверши и зафиксируй текущую тему в существующей ветке. Не создавай ветку
поверх случайного незакоммиченного набора файлов.

Коммиты — Conventional Commits. Примеры приведены в каждом этапе. Не переноси
результат в `dev` или `main`, если это не разрешено актуальной командой
пользователя и `AGENTS.md`.

## 2. Модель выполнения: не «вечный хаос», а непрерывные законченные циклы

### 2.1. Единица работы

Каждый пункт дорожной карты выполняй как отдельную единицу работы:

1. **Audit** — найди текущую реализацию и связанные тесты.
2. **Scope** — запиши, что входит и не входит в эту единицу.
3. **Contract** — сначала зафиксируй данные, permissions и API-контракт.
4. **Database** — при необходимости добавь миграцию и индексы.
5. **Backend** — реализуй service/repository/API с серверной авторизацией.
6. **Frontend** — добавь UI, состояния и локализацию.
7. **Tests** — негативные и позитивные сценарии.
8. **Manual verification** — реальный пользовательский сценарий кликами.
9. **Review** — перечитай diff, проверь секреты и миграции.
10. **Commit** — один логичный коммит законченной темы.
11. **Progress** — обнови журнал выполнения.

Не начинай следующую единицу, пока текущая не проходит её критерии приёмки.

### 2.2. Журнал прогресса

Создай `docs/IMPLEMENTATION_PROGRESS.md`, если такого журнала ещё нет. Не
используй его вместо тестов. Для каждого этапа записывай:

```markdown
## Phase N — название

- Status: not-started | in-progress | verified | blocked
- Branch:
- Commit:
- Implemented:
- Existing behavior reused:
- Migrations:
- Checks passed:
- Manual scenarios passed:
- Known limitations:
- Next phase:
```

В журнале запрещено писать «всё работает», если полный сценарий не проверен.

### 2.3. Управляемый цикл постоянных улучшений

После завершения всех обязательных фаз не останавливай развитие платформы, но
и не зацикливайся внутри незаконченной правки. Используй повторяемый цикл:

1. собери **Quality Radar** по категориям:
   - безопасность;
   - целостность данных;
   - модерация и злоупотребления;
   - доступность;
   - mobile UX;
   - производительность;
   - наблюдаемость;
   - качество тестов;
   - понятность интерфейса;
   - социальная ценность для НРИ-сообщества;
2. найди один самый важный доказуемый недостаток;
3. зафиксируй исходную метрику или воспроизводимый сценарий;
4. сформулируй ограниченную задачу и критерии приёмки;
5. реализуй её в отдельной ветке/коммите;
6. повтори проверку и сравни с исходным состоянием;
7. запиши результат в журнал;
8. перейди к следующему недостатку.

Приоритет выбирай по формуле:

```text
priority = user_impact × risk_reduction × confidence / implementation_cost
```

Сначала безопасность и потеря данных, затем блокирующие UX-проблемы, затем
производительность и только потом косметика.

Запрещено в цикле улучшений:

- бесконечно полировать один экран;
- придумывать функции без пользовательской ценности;
- добавлять зависимости ради тренда;
- выполнять массовый рефакторинг без измеримого результата;
- подменять незаконченный обязательный этап новой интересной задачей;
- создавать метрики, которые нарушают приватность;
- автоматически выкатывать результат в production.

### 2.4. Настоящие условия остановки

Остановись и запроси решение пользователя только если:

- требуется изменить `main` или remote;
- нужно удалить или необратимо преобразовать пользовательские данные;
- требуется реальный ключ, пароль, платёж или внешний аккаунт;
- найден конфликт с непонятными пользовательскими изменениями;
- нужно принять продуктовый выбор, существенно меняющий права или приватность;
- миграция потенциально блокирует большую production-таблицу;
- три последовательные попытки упираются в один внешний блокер.

Обычная ошибка теста не является блокером: разберись, исправь и перезапусти
узкую проверку.

### 3.2. Проверь незавершённые просмотры и закладки

Особое внимание удели возможной миграции, где `post_views` хранит `viewer_ip`
как обычный текст. Не храни сырой IP для аналитики просмотров. До применения
миграции измени дизайн на один из безопасных вариантов:

- HMAC IP с серверным секретом и периодически меняемой солью;
- краткоживущий privacy-preserving fingerprint;
- уникальность по авторизованному `viewer_id`, а для гостей — по короткоживущей
  анонимной cookie/hashed identifier;
- агрегирование без долгого хранения индивидуальных событий.

Если миграция уже применена где-либо, не редактируй её: создай следующую
миграцию, которая безопасно удалит или обезличит данные. Не заявляй анонимность,
если в БД остаётся исходный IP.

Проверь:

- уникальность просмотра в выбранном окне;
- исключение автора из собственного счётчика либо явное продуктовое решение;
- защиту от параллельных дублей;
- rate limit;
- отсутствие инкремента от prefetch/healthcheck;
- поведение гостей и авторизованных пользователей;
- индексы и срок хранения событий;
- атомарный `views_count` либо вычисление из событий без рассинхронизации.

### 3.3. Стабилизируй текущую ветку

Для уже начатых feed/editor/MCP изменений:

- сопоставь реализацию с фактическими API-контрактами;
- не принимай MCP-пароли через tool arguments;
- для cookie-мутаций отправляй разрешённый `Origin`;
- используй внешний API origin `http://localhost:8080` по умолчанию, если
  актуальная конфигурация не говорит иначе;
- не дублируй конфигурацию Editor.js между inline и full-page editor;
- проверь versioned/per-user draft;
- проверь orphaned draft images;
- обнови Docker dependency stages при добавлении workspace-пакета;
- stdio MCP не должен писать диагностические логи в stdout.

### 3.4. Критерии приёмки Phase 0

- capability matrix основана на коде и тестах;
- текущий diff понятен и не содержит случайных файлов;
- новые миграции безопасны для приватности;

## 4. Phase 1 — фундамент ролевой модели и permissions

### 4.1. Роли платформы

Нужны ровно три основные роли сайта:

- `admin` — владелец и полный администратор платформы;
- `moderator` — модерация пользователей и публичного контента без доступа к
  системным секретам;
- `user` — обычный участник.

Не путай роль сайта с ролями совместного редактирования персонажа
`owner`/`editor`. Это две разные оси доступа.

Иерархия:

```text
admin > moderator > user
```

Но не реализуй проверки как хаотичные сравнения строк. Создай централизованный
слой permissions.

### 4.2. Матрица полномочий

| Permission | admin | moderator | user |
|---|:---:|:---:|:---:|
| Использовать обычные функции сайта | ✓ | ✓ | ✓ |
| Просматривать очередь жалоб | ✓ | ✓ | — |
| Обрабатывать жалобы | ✓ | ✓ | — |
| Скрывать/восстанавливать публичный контент | ✓ | ✓ | — |
| Выносить предупреждение | ✓ | ✓ | — |
| Временно ограничивать пользователя | ✓ | ✓, в пределах политики | — |
| Перманентно блокировать пользователя | ✓ | — | — |
| Рассматривать апелляции | ✓ | ✓, не по своему решению | — |
| Видеть внутренние moderator notes | ✓ | ✓ | — |
| Видеть полный email пользователя | ✓ | маска либо только по необходимости | только свой |
| Назначать/снимать moderator | ✓ | — | — |
| Назначать/снимать admin | ✓, с защитой последнего admin | — | — |
| Менять AI provider/API key | ✓ | — | — |
| Видеть даже маску AI key | ✓ | — | — |
| Управлять системными настройками | ✓ | — | — |
| Просматривать аудит | ✓ | ограниченный moderation audit | — |
| Запускать опасные bulk actions | ✓ | только разрешённые | — |

### 4.3. Схема данных ролей

Сначала изучи текущее поле `profiles.is_admin`. Не ломай bootstrap первого
администратора.

Предпочтительная целевая модель:

```text
profiles.site_role: admin | moderator | user
```

Требования к миграции:

1. добавить `site_role` с безопасным default `user`;
2. backfill `is_admin = true` в `admin`;
3. все остальные профили в `user`;
4. добавить CHECK constraint;
5. обновить Kysely-типы;
6. временно поддержать чтение legacy `is_admin`, если это нужно для безопасного
   развёртывания;
7. удалить legacy поле только отдельной поздней миграцией после перевода всего
   кода и проверки rollback;
8. обеспечить существование хотя бы одного admin;
9. запретить удаление/понижение последнего admin на уровне service-транзакции.

PostgreSQL enum используй только после оценки безопасного изменения и rollback;
обычный text + CHECK часто проще развивать.

### 4.4. Централизованный permission service

Добавь в API единый типизированный механизм:

```text
requireRole(request, ...roles)
requirePermission(request, permission)
can(actor, permission, resource?)
```

Не оставляй старый `requireAdmin` как параллельную истину. Либо реализуй его как
тонкую обёртку поверх новой системы на время миграции, либо безопасно замени.

Permissions должны иметь literal union и исчерпывающие тесты. Проверка должна
происходить перед чтением чувствительных данных и до бизнес-мутации.

### 4.5. Управление ролями

Добавь admin-only API для изменения роли пользователя.

Обязательные защиты:

- администратор не может случайно понизить последнего admin;
- moderator не может менять роли;
- нельзя назначить неизвестную роль;
- операция выполняется транзакционно;
- все активные сессии пользователя при критическом изменении роли либо
  отзываются, либо роль перечитывается на каждом запросе;
- изменение роли попадает в audit log;
- API не позволяет массово повысить пользователей без явного списка ID;
- собственное понижение требует усиленного подтверждения в UI;
- role change защищён rate limit.

### 4.6. Тесты Phase 1

Минимально:

- user не открывает admin и moderation API;
- moderator открывает очередь жалоб, но не AI settings;
- moderator не меняет роли;
- admin меняет user ↔ moderator;
- неизвестная роль даёт 400;
- последний admin не может быть понижен или удалён;
- смена роли отражается в новой сессии/следующем запросе;
- отсутствие кнопки в UI не считается тестом защиты;
- legacy admin после миграции остаётся admin;
- миграции `up` и `down` проверены.

Рекомендуемый коммит:

```text

```

## 5. Phase 2 — неизменяемый аудит административных действий

### 5.1. Зачем аудит нужен раньше админки

Любая мощная админ-панель опасна без ответа на вопросы: кто, когда, что и по
какой причине изменил. Поэтому аудит делается до bulk actions и санкций.

### 5.2. Таблица audit events

Создай append-only таблицу, адаптируя название к стилю репозитория:

```text
admin_audit_events
- id uuid primary key
- actor_id uuid nullable only for internal system action
- actor_role text
- action text
- target_type text
- target_id text nullable
- reason text nullable
- metadata jsonb with redacted bounded payload
- request_id text nullable
- created_at timestamptz
```

Требования:

- индекс по `created_at desc`;
- индекс по `(target_type, target_id, created_at desc)`;
- индекс по `(actor_id, created_at desc)`;
- нельзя обновлять и удалять события через публичный API;
- metadata имеет ограничение размера на уровне приложения;
- не записывать пароль, session cookie, API key, содержимое приватных постов,
  полный IP и токены;
- для изменения значения сохранять безопасный diff `before`/`after`, только если
  поля не чувствительные;
- системные действия отличаются от действий человека;
- причины санкций и destructive actions обязательны.

### 5.3. Audit API и UI

Admin:

- список с cursor pagination;
- фильтры по actor/action/target/date;
- detail drawer/page;
- переход к связанному пользователю, посту или жалобе;
- JSON metadata показывать человекочитаемо, без сырого огромного dump.

Moderator видит только события модерации, необходимые для работы. Не видит AI
settings, системные секреты и admin role changes, если это не нужно политике.

### 5.4. Критерии приёмки Phase 2

- role change создаёт audit event;
- AI settings update создаёт redacted event без ключа;
- запрещённое действие не создаёт ложное событие успеха;
- failed action логируется только как failure с безопасной ошибкой, если это
  действительно полезно;
- audit API нельзя использовать как канал чтения секретов;
- пагинация стабильна при параллельных вставках.

Рекомендуемый коммит:

```text
feat(admin): add immutable administrative audit log
```

## 9. Phase 6 — полноценная система жалоб

### 9.1. Что можно пожаловаться

Поддержи жалобы как минимум на:

- пост;
- комментарий;
- профиль пользователя;
- персонажа;
- систему/шаблон;
- комментарий к системе.

Архитектура должна позволять расширение без создания невалидных target IDs.
Предпочитай схему с реальной ссылочной целостностью. Если выбран polymorphic
`target_type + target_id`, service обязан транзакционно проверять существование
и видимость target, а тесты — каждый target type.

### 9.2. Причины жалоб

Начальный набор:

- spam;
- harassment;
- hate_or_discrimination;
- sexual_content;
- violence_or_threat;
- personal_data;
- copyright;
- fraud_or_malicious_link;
- unsafe_for_minors;
- off_topic;
- other.

В UI причины локализованы и объяснены. `other` требует комментарий. Для угроз и
персональных данных очередь может получать высокий priority по прозрачному
правилу.

### 9.3. Схема report

Минимальные поля:

```text
- id
- reporter_id
- target kind/reference
- reason
- details, bounded text
- status: open | triaged | in_review | resolved | rejected | duplicate
- priority: low | normal | high | urgent
- assigned_moderator_id nullable
- resolution_code nullable
- resolution_note nullable
- duplicate_of nullable
- created_at
- updated_at
- resolved_at nullable
- target snapshot/redacted excerpt where legally and technically appropriate
```

Нужны индексы очереди, reporter history, target history и assignee.

### 9.4. Пользовательская отправка жалобы

- доступна из контекстного меню сущности;
- dialog доступен с клавиатуры;
- нельзя пожаловаться на несуществующий target;
- self-report либо запрещён, либо имеет понятное поведение;
- duplicate report того же reporter/target в открытом состоянии не создаёт
  бесконечные строки;
- rate limit и защита от abuse;
- reporter получает нейтральное подтверждение без обещания конкретной санкции;
- reporter не видит внутренние notes;
- автор контента не получает данные reporter;
- блокировка пользователя не должна препятствовать жалобе на опасный контент;
- жалоба не скрывает контент автоматически, кроме строго определённой emergency
  policy.

### 9.5. Очередь модерации

Нужны:

- вкладки new/assigned/mine/urgent/resolved;
- фильтры reason/target/priority/date/reporter/author;
- SLA indicator;
- назначение себе и другому moderator;
- блокировка конкурентного решения либо optimistic concurrency;
- preview target с безопасным контекстом;
- история предыдущих жалоб и санкций;
- связанные дубликаты;
- internal notes;
- набор допустимых resolution actions;
- обязательная причина решения;
- keyboard shortcuts только с подтверждением destructive action.

### 9.6. Решения по жалобе

Resolution codes:

- no_violation;
- content_hidden;
- content_restored;
- warning_issued;
- user_restricted;
- user_suspended;
- user_banned;
- duplicate;
- insufficient_context;
- referred_to_admin.

Одна жалоба может привести к нескольким действиям, но каждое действие отдельно
аудируется. Решение жалобы и модерационная мутация должны быть транзакционно
согласованы либо иметь безопасный workflow compensation.

### 9.7. Антиабьюз жалоб

- лимит жалоб на пользователя/период;
- duplicate collapse;
- detection повторных заведомо ложных жалоб на уровне правил;
- никакого автоматического бана только из-за количества жалоб;
- reporter reputation может быть только объяснимым внутренним сигналом;
- moderator всегда видит основание приоритета;
- запрещён скрытый AI verdict без human review;
- массовая атака жалобами не должна автоматически скрывать легальный контент.

### 9.8. Критерии приёмки Phase 6

- каждый target type покрыт integration test;
- user не читает чужую жалобу;
- author не узнаёт reporter;
- moderator может обработать report, но не получить admin secrets;
- два модератора не перезаписывают решение молча;
- duplicate report обрабатывается идемпотентно;
- санкция и resolution отражены в audit timeline;
- rate limit имеет локализованную ожидаемую ошибку;
- queue filters используют индексы.

Рекомендуемый коммит:

```text
feat(moderation): add reports and review queue
```

## 10. Phase 7 — санкции, ограничения и апелляции

### 10.1. Не своди всё к `is_banned`

Создай модель ограничений, которая может описать:

- warning;
- posting restriction;
- commenting restriction;
- reactions restriction;
- upload restriction;
- temporary account suspension;
- permanent ban.

Каждая санкция имеет:

- target user;
- kind;
- scope;
- reason code;
- moderator note;
- public/user-facing explanation;
- starts_at;
- expires_at nullable;
- created_by;
- source_report_id nullable;
- active/revoked/expired state;
- revoked_by/revoked_reason;
- created_at/updated_at.

### 10.2. Enforcement

Санкция должна реально применяться на API-границе. Например, hiding кнопки
комментария недостаточно: `POST /comments` обязан вернуть устойчивую ошибку.

Создай централизованный enforcement service, чтобы не размножать проверки по
всем route handlers.

Требования:

- чтение публичного контента остаётся доступным при ограничении публикаций;
- suspension отзывает активные сессии или блокирует их использование;
- expired sanction перестаёт действовать без ручного вмешательства;
- permanent ban только admin;
- moderator имеет максимальную длительность временной санкции;
- нельзя применить санкцию к admin через moderator API;
- self-sanction запрещён;
- системные фоновые операции не обходят ограничения случайно.

### 10.3. Апелляции

Пользователь должен:

- видеть активную санкцию и понятную причину;
- видеть срок;
- подать одну активную апелляцию на санкцию;
- добавить ограниченный текст;
- видеть статус без internal notes.

Правила рассмотрения:

- moderator не рассматривает апелляцию на собственное решение;
- admin может рассмотреть любую;
- решение имеет reason;
- одобрение снимает/изменяет санкцию транзакционно;
- отклонение не раскрывает внутренние данные;
- все действия аудируются;
- есть SLA/очередь просроченных апелляций.

### 10.4. Критерии приёмки Phase 7

- restriction реально блокирует соответствующий endpoint;
- разрешённые действия продолжают работать;
- истечение срока проверено управляемыми часами в тесте;
- moderator не банит admin и не выдаёт permanent ban;
- пользователь не создаёт две активные апелляции;
- собственный moderator не рассматривает апелляцию;
- снятие санкции немедленно восстанавливает доступ;
- session behavior документирован и протестирован.

Рекомендуемый коммит:

```text
feat(moderation): add user restrictions and appeals
```

## 11. Phase 8 — полноценная система просмотров и аналитики контента

### 11.1. Определения метрик

До кода письменно зафиксируй:

- **raw impression** — техническая загрузка карточки, не публичный счётчик;
- **qualified view** — сущность реально находилась в viewport достаточное время;
- **unique view** — qualified view одного viewer в заданном окне;
- **author view** — учитывается или нет;
- **bot/prefetch view** — не учитывается;
- временное окно дедупликации;
- retention индивидуальных событий;
- какие значения видит автор, moderator и admin.

Не называй все запросы «просмотрами».

### 11.2. Объекты просмотров

В конечном состоянии просмотры нужны для:

- постов;
- полноформатных статей;
- публичных персонажей;
- публичных систем/шаблонов;
- публичных профилей, если privacy policy это допускает.

Внедряй типы по одному, переиспользуя общий безопасный механизм. Не делай
несколько несовместимых таблиц без причины.

### 11.3. Privacy by design

- не хранить сырой IP как аналитику;
- не собирать browser fingerprint;
- не использовать email/username в event key;
- для гостей — короткоживущий анонимный идентификатор или HMAC;
- документировать retention;
- иметь cleanup job;
- агрегаты хранить дольше, индивидуальные события — минимально необходимое
  время;
- поддержать удаление/анонимизацию данных пользователя;
- не передавать аналитику третьей стороне без отдельного решения.

### 11.4. Надёжность счётчика

- endpoint идемпотентен в окне дедупликации;
- уникальность защищена индексом или транзакцией;
- параллельные запросы не завышают счётчик;
- удаление event history не уменьшает materialized lifetime count случайно;
- prefetch Next.js не считается;
- IntersectionObserver очищается при unmount;
- не создавай один HTTP-запрос на каждый краткий scroll event;
- batching допускается, если не усложняет надёжность;
- failure аналитики не ломает просмотр контента.

### 11.5. Авторская аналитика

Автор видит по своему контенту:

- уникальные просмотры;
- динамику за 7/30 дней;
- реакции;
- комментарии;
- добавления в избранное только агрегатом;
- conversion rates с понятным знаменателем.

Автор никогда не получает список конкретных зрителей или пользователей,
добавивших материал в избранное, если они явно не сделали публичное действие.

### 11.6. Admin analytics

Admin видит агрегаты платформы, но не получает ненужную возможность следить за
конкретным человеком. Любой drill-down должен иметь операционную цель и
permission.

Показывай:

- content views trends;
- active creators;
- engagement rate;
- retention cohorts только при достаточном размере группы;
- suspicious traffic spikes;
- error/drop rate event ingestion;
- storage и query cost.

### 11.7. Критерии приёмки Phase 8

- raw IP отсутствует в БД и логах;
- refresh не накручивает unique view;
- concurrent requests не накручивают счётчик;
- author privacy соблюдена;
- cleanup job протестирован;
- запросы используют индексы;
- UI корректен без JavaScript analytics;
- ошибка record-view не ломает feed/post page.

Рекомендуемый коммит:

```text
feat(analytics): add privacy-safe content views
```

## 14. Phase 11 — безопасность социальной платформы

Проведи отдельный threat-model review после появления мощной админки.

### 14.1. Авторизация и сессии

- server-side permission checks для каждого admin/moderation endpoint;
- изменение пароля отзывает остальные сессии;
- suspension и ban блокируют активные сессии;
- session fixation исключён;
- cookies сохраняют HttpOnly/SameSite/Secure policy;
- cookie mutation требует допустимый Origin;
- admin sensitive actions могут требовать недавнюю повторную аутентификацию;
- last-admin protection;
- role cache не оставляет старые права;
- session list не раскрывает token.

### 14.2. Abuse prevention

Rate limits отдельно для:

- auth;
- постов;
- комментариев;
- реакций;
- follows;
- reports;
- uploads;
- search;
- admin mutations;
- exports;
- MCP mutations.

Rate limit должен учитывать прокси-конфигурацию и не доверять произвольному
`X-Forwarded-For`.

### 14.3. Контент и XSS

- Editor.js blocks валидируются сервером;
- пользовательский HTML не рендерится напрямую;
- ссылки имеют safe protocols;
- изображения проверяются по сигнатуре и размеру;
- SVG не разрешать как пользовательскую картинку без безопасной sanitization;
- Markdown converter, если есть в MCP, не создаёт HTML injection;
- filenames не используются как storage key;
- удалённый embed не раскрывает приватный контент;
- CSV export защищён от formula injection.

### 14.4. SSRF и внешние интеграции

- AI base URL может менять только admin;
- запрет доступа AI provider URL к metadata/private networks, если endpoint
  делает серверные запросы к произвольному URL;
- MCP API origin проходит строгую валидацию;
- redirect policy не отправляет credentials на другой origin;
- webhooks, если появятся, имеют signatures и replay protection.

### 14.5. Секреты

- AI key никогда не возвращается браузеру;
- UI показывает только маску;
- moderator не видит AI settings;
- ключ не попадает в audit metadata и logs;
- saved admin key сейчас может быть защищён только `0600`, но не называй это
  шифрованием;
- подготовь интерфейс storage encryption, но не заявляй её без реализации;
- `.env.local` не читается и не коммитится;
- MCP stdout не содержит логов/секретов.

### 14.6. Административные действия

- destructive confirmation;
- обязательная причина;
- audit before/after без секретов;
- optimistic concurrency;
- bulk action limit;
- CSRF/origin protection;
- нельзя выполнить действие только подменой role в client state;
- moderator не может воздействовать на admin;
- admin не может удалить последнего admin;
- экспорт и удаление имеют отдельные permissions.

### 14.7. Security tests

Добавь regression tests для:

- horizontal privilege escalation;
- vertical privilege escalation;
- IDOR на reports, favorites, appeals и admin user detail;
- forged role body;
- missing/wrong Origin;
- hidden content leakage;
- secret leakage в JSON/log/audit;
- open redirect;
- unsafe URL schemes;
- report spam;
- concurrent role/sanction updates;
- last-admin race;
- CSV injection.

Рекомендуемый коммит:

```text
security: harden administration and social workflows
```

## 19. Phase 16 — MCP и внешние агенты после стабилизации permissions

Если `packages/mcp` существует, приведи его к новой ролевой модели.

### 19.1. Граница возможностей MCP

По умолчанию MCP обслуживает обычные пользовательские сценарии. Не выставляй
admin/moderation tools автоматически.

- credentials не являются аргументами LLM tools;
- предпочтительно использовать scoped personal access tokens;
- token scopes минимальны;

- server logs только stderr;

- API origin валидируется;
- redirect не уносит credentials;

- MCP tool schemas соответствуют `packages/contracts`;
- ошибки не содержат внутренние stack traces;
- rate limits применяются;
- destructive tools требуют явного подтверждения MCP host, если протокол и

credentials, permission audit и human confirmation.

### 19.3. MCP tests

- tool → API mapping;
- Zod/schema validation;
- cookie/token isolation;
- no secrets in result/error;
- no stdout diagnostics;
- wrong role rejected;
- revoked token rejected;
- redirects do not retain auth to another origin;
- mutation origin/security behavior;
- packaging/bin/shebang/files/Node version;

## 20. Полная стратегия тестирования

### 20.1. На каждой единице работы

Минимум:

```bash
git diff --check
```

Плюс полный просмотр собственного diff.

### 20.2. Контракты

- valid input;
- invalid input;
- неизвестные enum values;
- boundary lengths;
- публичные response schemas не содержат секретов;
- RU/EN структуры ключей совпадают.

### 20.3. Миграции

- clean `up`;
- безопасный `down`;
- upgrade с существующими данными;
- backfill legacy admin;
- constraints;
- indexes;
- foreign key deletion behavior;
- concurrent last-admin change;
- dist migrations sync.

### 20.4. API integration tests

Для каждой роли:

- anonymous;
- user;
- moderator;
- admin.

Проверяй не только success, но и:

- 400 validation;
- 401 authentication;
- 403 permission/origin;
- 404 non-disclosure;
- 409 concurrency/conflict;
- 429 rate limit;
- идемпотентность;
- rollback при ошибке;
- audit side effects;
- отсутствие secret fields.

### 20.5. Web tests

- permission-aware navigation;
- loading/empty/error/forbidden;
- optimistic rollback;
- dynamic comments/reactions/favorites;
- report dialog;
- moderation queue filters;
- role change confirmation;
- last-admin error;
- mobile admin drawer;
- keyboard flow;
- message localization.

### 20.6. E2E-сценарии

Обязательный набор:

#### Обычный пользователь

1. зарегистрироваться/войти;
2. настроить профиль;
3. создать пост с текстом и embed;
4. сохранить другой пост;
5. добавить реакцию и комментарий;
6. отправить жалобу;
7. увидеть статус жалобы без внутренних данных;
8. проверить saved page;
9. выйти.

#### Модератор

1. войти как moderator;
2. увидеть moderation navigation;
3. не открыть AI settings и role management;
4. назначить жалобу себе;
5. просмотреть безопасный контекст;
6. вынести warning/temporary restriction;
7. завершить report;
8. увидеть audit event;
9. не суметь заблокировать admin.

#### Администратор

1. войти как admin;
2. увидеть overview;
3. назначить пользователя moderator;
4. найти профиль и контент;
5. рассмотреть апелляцию;
6. проверить AI settings без утечки ключа;
7. проверить jobs/storage/audit;
8. попытаться понизить последнего admin и получить безопасный отказ.

#### Приватность

1. пользователь A сохраняет пост;
2. пользователь B не видит факт сохранения;
3. автор видит только aggregate;
4. moderator не видит лишние private bookmark details;
5. пользователь удаляет/скрывает контент;
6. старое notification/report preview не раскрывает содержимое.

#### Просмотры

1. карточка мелькнула менее порога — view не записан;
2. находилась в viewport — записан;
3. refresh в окне не увеличивает unique count;
4. другой viewer увеличивает;
5. ошибка endpoint не ломает страницу;
6. raw IP нигде не сохранён.

### 20.7. Docker verification

При новых зависимостях:

```bash
docker compose run --rm deps
```

При миграциях:

```bash
docker compose run --rm migrate
```

Для полного check используй процедуру из `AGENTS.md`, включая сборку внутренних
пакетов. После изменения Docker/package manifests обязательно проверь build.

Не утверждай, что сервис healthy, пока не проверены `docker compose ps`, API,
web, proxy и логи worker.

### 20.8. Browser verification

Открой реальный `http://localhost:8080` и проверь кликами:

- 390px mobile;
- обычный tablet;
- 1440px desktop;
- keyboard only;
- отсутствие console errors;
- network failures;
- slow loading;
- empty states;
- role-specific routes.

Тестовые данные агента маркируй предсказуемым префиксом и удаляй после проверки,
если они не нужны пользователю. Не удаляй чужие данные.

## 21. Definition of Done для любой функции

Функция считается законченной только если:

- [ ] существующая реализация предварительно изучена;
- [ ] границы задачи записаны;
- [ ] permissions определены;
- [ ] контракт валидирует untrusted input;
- [ ] миграция имеет `up`, `down`, constraints и indexes;
- [ ] Kysely types синхронизированы;
- [ ] API не раскрывает секреты;
- [ ] бизнес-операция транзакционно безопасна;
- [ ] concurrency рассмотрена;
- [ ] rate limit рассмотрен;
- [ ] audit event добавлен для admin/moderation mutation;
- [ ] RU и EN обновлены;
- [ ] loading/empty/error/disabled состояния реализованы;
- [ ] mobile и desktop проверены;
- [ ] keyboard и screen reader semantics проверены;
- [ ] позитивные и негативные тесты проходят;
- [ ] `git diff --check` проходит;
- [ ] diff перечитан;
- [ ] нет секретов/дампов/артефактов;
- [ ] журнал прогресса обновлён;
- [ ] создан логичный коммит, если Git разрешён.

## 23. Формат отчёта после каждой фазы

Не пиши длинный рассказ о процессе. Дай фактический отчёт:

```markdown
## Phase N complete — название

### Для пользователя
- Что стало доступно.

### Безопасность и данные
- Permissions.
- Миграции.
- Retention/privacy решения.

### Проверки
- Команда — результат.
- E2E-сценарий — результат.
- Mobile/desktop — результат.

### Git
- Branch.
- Commit.
- Main untouched: yes/no.

### Ограничения
- Что реально осталось.
- Почему это не скрыто под фразой «всё работает».

### Следующий этап
- Точное название следующей единицы работы.
```

Если тест падает, укажи точную команду и причину. Не выдавай старую ошибку за
ошибку своего изменения, но и не скрывай её.

## 24. Строгий порядок выполнения

Не перескакивай через фундамент ради красивого UI.

1. Phase 0 — аудит и стабилизация текущей работы.
2. Phase 1 — роли и permissions.
3. Phase 2 — audit log.
4. Phase 3 — admin shell и overview.
5. Phase 4 — управление пользователями и профилями.
6. Phase 5 — content inventory и moderation states.
7. Phase 6 — жалобы и moderation queue.
8. Phase 7 — санкции и апелляции.
9. Phase 8 — privacy-safe просмотры и аналитика.
10. Phase 9 — избранное и коллекции.
11. Phase 10 — уведомления.
12. Phase 11 — security hardening.
13. Phase 12 — jobs/storage/system operations.
14. Phase 13 — privacy/data lifecycle.
15. Phase 14 — измеренная оптимизация.
16. Phase 15 — social/TRPG UX polish.
17. Phase 16 — MCP permissions alignment.
18. Полный сквозной аудит и release candidate report.
19. Quality Radar — по одной измеримой задаче за цикл.

Если функция следующего этапа уже существует, не пропускай этап молча. Проведи
аудит, добавь отсутствующие тесты/permissions/доступность, зафиксируй `verified`
и только затем двигайся дальше.

## 25. Финальная команда агенту

Начни с чтения `AGENTS.md`, `git status`, текущего diff, миграций, контрактов и
тестов. Создай capability matrix и журнал прогресса. Сначала стабилизируй уже
начатую работу, не потеряв пользовательские изменения. Затем выполняй фазы
строго по порядку.

Не ограничивайся красивыми страницами: каждая кнопка должна иметь реальную
серверную permission-проверку, устойчивую модель данных, аудит и тест.

Не ограничивайся backend: каждый законченный сценарий должен быть понятен,
доступен, локализован и проверен в реальном браузере.

Не называй кнопку жалобы системой модерации, счётчик — аналитикой, boolean
`is_admin` — полноценной RBAC, а маску ключа — шифрованием.

Сделай MyCharacter социальной платформой, которой можно доверить сообщество
людей: с сильной админкой, понятными полномочиями, уважением к приватности,
обратимыми модерационными решениями и инженерной дисциплиной.

После завершения обязательных фаз перейди к Quality Radar и продолжай
последовательные измеримые улучшения, пока пользователь не остановит работу или
не возникнет настоящий блокер из раздела 2.4.
