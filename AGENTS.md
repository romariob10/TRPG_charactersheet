# AGENTS.md — правила работы с MyCharacter

Этот файл — обязательный рабочий контракт для любого AI-агента, который меняет
репозиторий. Он специально написан так, чтобы даже небольшая и недорогая модель
могла безопасно выполнять локальные правки, не ломая архитектуру, данные и Git.

## 1. Главный принцип

Делай минимальное изменение, которое полностью решает запрос пользователя.

- Не расширяй задачу «заодно».
- Не переписывай работающий код ради вкусовщины.
- Не обновляй зависимости, версии, формат всего проекта или Docker-образы без
  причины, связанной с задачей.
- Не меняй публичное поведение, API, схему БД или формат данных молча.
- Если требование можно понять двумя существенно разными способами и выбор
  повлияет на данные, безопасность или UX — остановись и задай один конкретный
  вопрос.
- Если разумное безопасное предположение не меняет смысл задачи — сделай его,
  явно упомяни в результате и продолжай.

## 2. Перед любой правкой

Всегда выполни короткую разведку:

1. Прочитай этот файл целиком.
2. Выполни `git status --short --branch`.
3. Найди связанные файлы через `rg` / `rg --files`.
4. Прочитай существующую реализацию, тесты и соседние компоненты.
5. Проверь, нет ли незакоммиченных пользовательских изменений в тех же файлах.
6. Сформулируй для себя точную границу задачи и список затрагиваемых пакетов.

Не начинай писать код, опираясь только на имя файла или догадку о структуре.

Если рабочее дерево уже грязное:

- считай все существующие изменения собственностью пользователя;
- не удаляй, не откатывай и не форматируй их без необходимости;
- отделяй свои изменения максимально узко;
- если правка пересекается с непонятным пользовательским изменением — сначала
  сообщи об этом и попроси решение.

## 3. Git: обязательная политика

### Ветки

- `main` — защищённая стабильная ветка. Никогда не коммить, не merge и не
  cherry-pick в `main` без отдельного явного подтверждения пользователя именно
  на это действие.
- Основная ветка разработки — `dev`.
- Любая работа выполняется в подветке, созданной от актуального локального
  `dev`.
- Для агентских веток используй имя `codex/<тип>-<короткая-тема>`, например:
  `codex/fix-feed-spacing`, `codex/chore-copy`, `codex/feat-post-editing`.
- Перед созданием ветки проверь, что находишься на `dev`, а рабочее дерево не
  содержит изменений, которые могут потеряться.
- Не выполняй `git pull`, `git fetch`, push или операции с remote, если
  пользователь этого не просил.

Безопасный шаблон начала работы:

```bash
git status --short --branch
git switch dev
git switch -c codex/<тип>-<тема>
```

Если ветка для текущей задачи уже создана — продолжай в ней, не создавай новую
без причины.

### Запрещённые Git-операции

Без прямого разрешения пользователя запрещены:

- `git reset --hard`;
- `git checkout -- <file>` и `git restore <file>` для чужих изменений;
- `git clean`;
- rebase опубликованной ветки;
- force-push;
- amend чужого коммита;
- удаление веток и тегов;
- изменение истории `main` или `dev`.

Не используй Git как способ «починить» непонятное состояние. Сначала разберись,
что изменено и кому принадлежат изменения.

### Коммиты

- Не создавай коммит, если пользователь просил только показать, объяснить,
  диагностировать или подготовить вариант.
- Если пользователь попросил закончить изменение с Git — сделай один логичный
  коммит на одну законченную тему.
- Перед коммитом обязательно проверь:
  - `git status --short`;
  - `git diff --check`;
  - `git diff --stat`;
  - полный diff своих изменений;
  - отсутствие секретов, временных файлов, дампов и тестовых артефактов.
- Не добавляй всё через `git add .`, если в дереве есть несвязанные изменения.
  Перечисляй конкретные файлы или каталоги задачи.
- Используй Conventional Commits:
  - `fix: ...` — исправление поведения;
  - `feat: ...` — новая пользовательская возможность;
  - `chore: ...` — обслуживание без изменения продукта;
  - `docs: ...` — только документация;
  - `test: ...` — только тесты;
  - `refactor: ...` — изменение структуры без изменения поведения.
- Сообщение должно описывать результат, а не процесс: `fix: keep reactions in
  sync`, а не `fix: changed files`.

После проверенного коммита подветку можно fast-forward в `dev`, только если это
входит в запрос пользователя. `main` при этом остаётся нетронутым.

### Версии и релизы

- Не повышай версию по собственной инициативе.
- Версии корневого пакета, приложений и внутренних пакетов должны оставаться
  согласованными, если пользователь запросил релиз.
- Релизный коммит оформляется отдельно и только после всех проверок:
  `release: preview X.Y.Z`.
- Не создавай тег и не переноси релиз в `main` без явного подтверждения.
- Текущее состояние проекта: рабочая разработка ведётся от `dev`; `main` должен
  оставаться чистой стабильной историей до команды пользователя.

## 4. Карта репозитория

Это pnpm-монорепозиторий TypeScript:

- `apps/web` — Next.js 16, React 19, Tailwind CSS, `next-intl`;
- `apps/api` — Fastify API, авторизация, realtime и бизнес-логика;
- `apps/worker` — фоновые задания `pg-boss`, PDF-каталогизация и AI vision;
- `packages/contracts` — общие Zod-схемы и публичные TypeScript-типы;
- `packages/database` — Kysely, типы таблиц и миграции PostgreSQL;
- `packages/pdf` — обработка PDF и OCR;
- `packages/storage` — файловое и S3-совместимое объектное хранилище;
- `compose.yaml` — локальная разработка и тестовые сервисы;
- `compose.prod.yaml` — production-конфигурация;
- `README.md` и `.env*.example` — пользовательская документация конфигурации.

Не дублируй один и тот же контракт между web и API. Общие схемы и типы должны
жить в `packages/contracts` и экспортироваться через его `src/index.ts`.

## 5. Правила написания кода

### Общие правила TypeScript

- Сохраняй строгую типизацию. Не добавляй `any`, `as any`, `@ts-ignore` или
  отключение ESLint ради прохождения проверки.
- `unknown` с явной проверкой безопаснее, чем принудительный cast.
- Используй ранние возвраты и небольшие функции с одной ответственностью.
- Имена должны описывать смысл предметной области, а не техническую форму.
- Не создавай абстракцию для одного тривиального вызова. Но и не копируй одну
  бизнес-логику в несколько приложений.
- Следуй стилю соседних файлов: ESM, расширения `.js` во внутренних Node-import,
  существующий порядок импортов и текущие форматтеры.
- Не оставляй закомментированный код, отладочные `console.log`, TODO без
  объяснения или мёртвые компоненты.
- Комментарий должен объяснять причину или ограничение, а не пересказывать код.
- Не форматируй несвязанные файлы.

### Контракты и валидация

- Любые входные данные из HTTP, Editor.js, env, файлов и внешних AI API считаются
  недоверенными.
- Проверяй вход через Zod или точную ручную проверку там, где Zod неприменим.
- Для новой общей сущности:
  1. добавь схему в `packages/contracts/src`;
  2. экспортируй её из `packages/contracts/src/index.ts`;
  3. выведи тип через `z.infer`, не дублируй интерфейс вручную;
  4. используй схему на API-границе;
  5. добавь тест валидного и невалидного ввода.
- Не возвращай в публичные схемы секреты, внутренние storage keys, хеши паролей
  и служебные данные.

### API

- Маршруты находятся в `apps/api/src/modules/<domain>/routes.ts`.
- Бизнес-логика и запросы к БД должны быть вынесены из обработчика в service или
  repository, если обработчик перестаёт быть простым адаптером HTTP.
- Защищённый маршрут обязан явно вызвать `requireActor`; административный —
  `requireAdmin`.
- Проверяй body, params и query до бизнес-логики.
- Ожидаемые ошибки возвращай через `AppError` с устойчивым машинным `code` и
  корректным HTTP-статусом.
- Не раскрывай детали внутренних исключений клиенту. Не проглатывай
  неожиданные ошибки без логирования.
- Для изменяющих состояние публичных действий учитывай rate limit, права
  доступа, идемпотентность и конкурентные запросы.
- Не создавай конфликтующие параметризованные маршруты. Например,
  `/:username/:slug` и `/:id/comments` имеют одинаковую форму — публичные
  маршруты нужно выносить под отдельный префикс.
- Для связанных записей используй транзакцию, если частичный успех оставит БД
  в неконсистентном состоянии.

### База данных и миграции

- Не изменяй уже применённую миграцию. Создавай новую миграцию с UTC timestamp в
  имени: `YYYYMMDDHHMM_description.ts`.
- Миграция обязана иметь безопасные `up` и `down`.
- Добавляй внешние ключи, `onDelete`, уникальные ограничения, check constraints
  и индексы осознанно.
- После изменения схемы синхронно обнови `packages/database/src/types.ts`.
- Обнови migration tests и проверку dist migrations.
- Не удаляй пользовательские данные и не делай потенциально долгую
  необратимую миграцию без отдельного согласования.
- JSON/JSONB для node-postgres сериализуй явно, когда значение может быть
  воспринято как PostgreSQL array.
- Интеграционные тесты должны использовать `createTestDatabase` и очищать свои
  ресурсы.

### Хранилище и загрузка файлов

- Работай через интерфейс `ObjectStorage`, а не напрямую с локальной файловой
  системой в API-модулях.
- Локальное хранилище и S3 должны сохранять одинаковую семантику `put`, `stat`,
  `open`, `delete` и range-запросов.
- Каждый storage key обязан пройти `assertStorageKey`; при добавлении нового
  типа объекта расширяй whitelist максимально узко и добавляй тест.
- Проверяй размер и сигнатуру файла, а не только MIME и расширение от клиента.
- Сначала обеспечь согласование БД и объекта. При ошибке удаляй только объект,
  созданный текущей операцией.
- Никогда не печатай S3 credentials, AI keys, cookie или содержимое `.env.local`.

### Web / React / Next.js

- По умолчанию используй Server Components. Добавляй `"use client"` только
  компонентам с состоянием, эффектами, браузерными API или обработчиками.
- Серверные запросы выполняй через `apps/web/src/lib/api/server.ts`, клиентские
  — через `apps/web/src/lib/api/client.ts`.
- Не передавай секреты и лишние данные из server component в client component.
- Тяжёлые браузерные библиотеки вроде Editor.js загружай динамически только в
  момент использования.
- Не вызывай setState родителя внутри render или functional updater дочернего
  компонента.
- Оптимистичное обновление обязано иметь точный rollback при ошибке.
- Для асинхронных эффектов учитывай unmount, гонки и очистку listeners/timers.
- Не используй `dangerouslySetInnerHTML` для пользовательского контента.
  Editor.js-данные нормализуются на сервере и рендерятся безопасными React
  узлами.
- Все интерактивные элементы должны быть доступны с клавиатуры и иметь label,
  `aria-label`, `aria-expanded` или `aria-pressed`, где это уместно.
- Лента и основные пользовательские сценарии обязаны быть адаптивными. Проверяй
  минимум узкую мобильную и обычную desktop-ширину.
- Не копируй дизайн референсов буквально; переноси только понятные UX-паттерны.

### Локализация

- Пользовательский интерфейс поддерживает русский и английский.
- Любой новый видимый текст добавляй одновременно в
  `apps/web/messages/ru.json` и `apps/web/messages/en.json`.
- Не оставляй русские или английские строки прямо в компонентах, кроме
  технических значений, которые не показываются пользователю.
- После изменения сообщений проверь, что оба JSON-файла валидны и содержат
  одинаковую структуру ключей.

### CSS и дизайн

- Используй существующие CSS variables и компоненты из `components/ui`.
- Не вводи второй набор цветов, радиусов или кнопок для одной мелкой задачи.
- Сохраняй текущую визуальную систему, состояния hover/focus/disabled и
  достаточный контраст.
- Избегай глобальных CSS-правил, если стиль относится к одному компоненту.
- Не добавляй анимацию, если она ухудшает отзывчивость или не учитывает
  `prefers-reduced-motion`.

## 6. Безопасность и приватность

- Никогда не читай и не выводи секреты из `.env.local`, `.env.prod`, Docker
  secrets, cookies, локального storage браузера или файлов настроек.
- Не коммить:
  - реальные API keys и пароли;
  - `.env.local` / `.env.prod`;
  - дампы БД, backups, загруженные PDF и изображения пользователей;
  - логи с персональными данными;
  - временные файлы и browser artifacts.
- API-ключ AI из админ-панели хранится только на сервере, не возвращается в
  браузер и в UI показывается только маска. Сейчас файл защищён правами `0600`,
  но не зашифрован на диске — не утверждай обратное.
- `AI_PRIMARY_API_KEY` имеет приоритет над legacy `AI_API_KEY`; сохранённая
  администратором настройка имеет приоритет над env.
- Любое действие администратора должно проверяться на сервере. Скрытая кнопка
  в UI не является защитой.
- Не ослабляй CORS, cookie flags, origin checks, rate limits или валидацию ради
  удобства локального теста.

## 7. Зависимости

- Сначала проверь, нельзя ли решить задачу уже установленными средствами.
- Не добавляй пакет ради нескольких строк простого кода.
- Если пакет действительно нужен:
  - используй `pnpm` и workspace filter;
  - выбирай официальный или широко поддерживаемый пакет;
  - не меняй package manager;
  - коммить `package.json` и `pnpm-lock.yaml` вместе;
  - проверь bundle/runtime impact и среду Node/browser;
  - обнови Docker dependency volume перед запуском стека.
- Не выполняй массовое обновление lockfile или major upgrade в рамках мелкой
  правки.

## 8. Проверки: выбирай по риску

Ни одна задача не считается завершённой без проверки. Сначала запускай самые
узкие релевантные проверки, затем расширяй их пропорционально риску.

### Минимум для любой правки

```bash
git diff --check
```

Также перечитай изменённый diff целиком.

### Документация или перевод

- проверь JSON сообщений парсером;
- запусти lint/typecheck web, если менялись ключи, которые использует код;
- убедись, что команды и пути в документации существуют.

### Изменение одного TypeScript-пакета

```bash
pnpm --filter <package-name> lint
pnpm --filter <package-name> typecheck
pnpm --filter <package-name> test
```

Примеры имён: `@mycharacter/web`, `@mycharacter/api`,
`@mycharacter/storage`, `@mycharacter/database`.

### Изменение нескольких слоёв или общего контракта

```bash
pnpm -r lint
pnpm -r typecheck
```

Затем запусти тесты затронутых пакетов. Для законченной сквозной фичи нужен
полный `pnpm check` в корректно подготовленной среде.

### API и PostgreSQL integration tests

На хосте `DATABASE_URL` может отсутствовать. Используй Docker и сначала собери
внутренние runtime-пакеты:

```bash
docker compose --profile test build check
docker compose --profile test run --rm check sh -c \
  "pnpm --filter @mycharacter/database build && \
   pnpm --filter @mycharacter/storage build && \
   pnpm --filter @mycharacter/pdf build && \
   pnpm check"
```

Для маленькой API-правки допустим узкий Vitest-файл после тех же трёх build.
Не объявляй весь проект проверенным, если запускал только один тест.

### UI-проверка

Если менялось пользовательское поведение:

- открой реальный локальный сайт через `http://localhost:8080`;
- проверь основной сценарий кликами, а не только наличие DOM;
- проверь loading, empty, error и disabled состояния;
- проверь отсутствие console/runtime ошибок;
- проверь mobile и desktop layout;
- тестовые аккаунты и данные, созданные агентом, удали после проверки, если они
  не нужны пользователю.

## 9. Docker

- Не запускай `docker compose down -v`. Это удалит постоянные данные.
- Не удаляй volumes, базу или S3-объекты без явного разрешения.
- Если изменились зависимости:

```bash
docker compose run --rm deps
```

- Если добавлена миграция:

```bash
docker compose run --rm migrate
```

- Если пользователь попросил пересобрать приложение или изменились Dockerfile,
  зависимости либо runtime-конфигурация:

```bash
docker compose build web api worker migrate
docker compose up -d --force-recreate api worker web proxy
docker compose ps
```

- После запуска дождись `healthy` для API, web и proxy. У worker нет отдельного
  healthcheck — проверь лог готовности и отсутствие циклических падений.
- Не утверждай, что Docker пересобран или сервис healthy, пока не проверил это
  фактически.

## 10. Специальный протокол для мелких правок

Для текста, отступа, цвета, label, локализации или маленького поведения:

1. Найди единственный источник значения.
2. Измени минимальное количество строк.
3. Не рефактори соседний код.
4. Если текст виден пользователю — обнови RU и EN.
5. Запусти lint/typecheck затронутого приложения.
6. Для UI визуально проверь конкретное место.
7. Покажи пользователю краткий итог и точную проверку.

Мелкая правка не является оправданием пропустить проверку, но и не должна
превращаться в переписывание страницы.

## 11. Когда нужно остановиться

Остановись и запроси решение пользователя, если:

- требуется тронуть `main`;
- нужно удалить или необратимо преобразовать пользовательские данные;
- требуется реальный API key, пароль, платёж или доступ к внешнему аккаунту;
- обнаружены конфликтующие незакоммиченные изменения пользователя;
- задача требует смены архитектуры, провайдера или публичного API, хотя запрос
  был про маленькую правку;
- проверка требует опасного ослабления безопасности;
- три последовательные попытки упираются в один внешний блокер.

Не останавливайся из-за обычной ошибки lint/test: сначала прочитай ошибку,
исправь причину и перезапусти узкую проверку.

## 12. Формат финального отчёта

Пиши кратко и по фактам:

- что изменено для пользователя;
- какие проверки реально прошли;
- какая ветка и коммит созданы, если Git был частью задачи;
- что осталось настроить или проверить вручную;
- любые важные ограничения или сделанные предположения.

Не говори «всё работает», если не проверил основной сценарий. Не скрывай
падающие тесты и не выдавай старые ошибки за ошибки текущего изменения.
